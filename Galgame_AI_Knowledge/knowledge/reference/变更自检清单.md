# 变更自检清单（工具开发会话用；**对外发布前的强制关卡**）

**为什么有这份文件**：工具开发会话反复犯**同一类错**——
改动本身对了，但**没检查连锁影响**，于是每次都由用户或外部审阅者兜底。
本清单把"发布前必须自查什么"固定下来，**不靠记性，靠逐条打勾**。

**适用**：任何对 `Galgame_AI_Knowledge\` 下文档的实质性改动（新增文件、改规则、改编号、改引用）。
**维护者**：工具开发会话。**版本**：v1（2026-10-12 建立）

---

## 零、三段式审阅流程（用户 2026-10-12 指定，此后照做）

```
① 工具开发会话做完 → 先按本清单自查（逐条打勾，不许跳）
        ↓
② 交 wuddy（CodeBuddy CLI）核对一轮
        ↓
③ 用户再交 Gemini 核对一轮
        ↓
④ 工具开发会话逐条核验她们的报告（真假、漏没漏），最后自己再看一遍她们漏掉的
```

**关键**：**① 是前置关卡，不是可选步骤。** 前两轮的问题全部逃过了①，
根因就是①根本不存在。

**② 的用法**（别忘它的限制）：
```powershell
$node = "C:\Users\salat\.workbuddy-ai\binaries\node\versions\22.22.2-2\node.exe"
$cli  = "C:\Users\salat\AppData\Local\Programs\WorkBuddyAI\resources\app.asar.unpacked\cli\dist\codebuddy-headless.js"
'【只读】审阅任务…【只给结论，简洁】' | & $node $cli -p --permission-mode bypassPermissions
```
- 需 `danger-full-access`（它要写自身缓存）
- prompt 里写明「只读、只给结论、简洁」
- **它的结论同样要回源核验后才采信**
- 若报 `Windows Job runner exited with exit code 5`：是环境问题，**重试或改人工**，不要死磕

## 一、A 类：引用完整性

| # | 检查项 | 怎么查 |
|---|---|---|
| A1 | **被引用路径真实存在** | 逐条 `Test-Path`。**尤其**：改动中新增/改名的文件 |
| A2 | **被引用的"节"真实存在** | 按**标题**检索（如 `语体规则`），**不要按编号猜**；区分"引用本文档的节"与"引用外部文件的节" |
| A3 | **行号锚点可回源** | `file:line` 逐条回 `cleaned\messages.jsonl` 或对应语料核对 |
| A4 | **跨文档同一事实说法一致** | 同一事实（版本号、天号、路径、文件名）在**所有**提到它的文档里一致 |

> **A2 的教训**：曾用字面串搜「第七节」（档案实际写作 `## 七、…`）就断言"该编号不存在"，
> 并把错误结论传染 4 处。**否定式结论必须附检索命令与原始输出。**

## 二、B 类：结构完整性（Markdown 实际渲染）

| # | 检查项 | 怎么查 |
|---|---|---|
| B1 | **表格未被空行切断** | 逐行检测「表行 - 空行 - 表行」的断裂 |
| B2 | **代码栅栏成对** | 统计 ` ``` ` 与 ` ```text ` 数量并定位 |
| B3 | **列表编号连续、无重复** | 正则提取编号后与 `1..N` 比对 |
| B4 | **没有截断**（编辑误伤） | 检查文件尾部与改动处上下文 |

> **B1 的教训**：曾把新表格行追加到**原表之外的另一个块**，中间隔了空行——
> **Markdown 里渲染不出表格**，而我自己"看着觉得对"。

## 三、C 类：新规定的传达（**用户特别要求**）

| # | 检查项 | 判断标准 |
|---|---|---|
| C1 | **扮演者能知道吗？** | 新规定是否写进**扮演者的入口**（`新会话启动提示词.md` 扮演者段 / `PROJECT_STATE.md` §5 或 §7 / 读取顺序）？ |
| C2 | **归档者能知道吗？** | 是否写进**归档者的入口**（`双会话提示词与新工作注意事项.md` 第二部分 / `归档划界规则.md`）？ |
| C3 | **已在跑的会话怎么办？** | 若两个会话都已在运行，**明确告诉用户**：文件改了、运行中的会话不会自动知道；并**给出可转发的说明**（或建议等归档后开新会话自然生效） |
| C4 | **有没有生产"死文档"？** | 新写的文件**有没有入口指向它**？没有入口的文件等于不存在 |
| C5 | **是否制造了重复来源？** | 同一内容抄了几处？**只留一处权威，其余"指向它"** |

> **C4 的教训**：两张横切表做出来后**没有任何入口**，扮演者读不到——
> 是用户问「没给她们看吗」才发现的。
> **C5 的教训**：同一内容抄两处（文件正文＋提示词内联摘要），改一处漏一处；
> 本会话因此把同一个错误传染到 4 处。

## 四、D 类：事实与陈旧

| # | 检查项 | 怎么查 |
|---|---|---|
| D1 | **路径是否仍有效** | 绝对路径逐个 `Test-Path`（本机路径会消失） |
| D2 | **版本号/日期是否最新** | 与 `git log`、规范版本号比对 |
| D3 | **旧编号/旧文件名是否残留** | 全文搜历史编号（如旧章节号、旧文件名） |
| D4 | **占位符是否还在** | 搜「待补」「留空」「未创建」等，判断是否已该填 |
| D5 | **本地数据事实是否被搞反** | 如 `.gitignore` 排除 ≠ 文件不存在；先查再断言 |

## 五、E 类：改动无误

| # | 检查项 | 怎么查 |
|---|---|---|
| E1 | **变量替换完好** | `{{user}}` / `{{char}}` 等未被破坏（**注意别写成 `{ {user} }`**） |
| E2 | **原文引用未被改错** | 改引用时回源核对**完整句**（截断会产生假阳性；引用可能跨行合并） |
| E3 | **密钥扫描 0 命中** | 提交前扫 `sk-` / `AKIA` / `ghp_` / 私钥块 |
| E4 | **`reports/sessions/` 未入库** | `git ls-tree -r --name-only HEAD \| Select-String 'reports/sessions'` |

## 六、发布前必须产出的三件事

按用户既定格式，**每次改动都要给**：

1. **动了哪些文件**（含新增/删除）
2. **提交号**（以及是否已推送）
3. **怎么回退**（`git revert <提交号>`）

**另加**（本清单要求）：
4. **A–E 五类自查结果**（逐类写明"已查/无此情况"，**不许留空**）
5. **若涉及新规定**：C1–C3 的传达确认（写进哪个入口、运行中的会话怎么办）

---

## 七、自检结果的记录方式（防止"声称查过"）

**每条检查都要能给出证据**，例如：

```
A1 引用路径：16 条，逐条 Test-Path → 全部存在
A2 引用节号：按标题检索「语体规则」→ 7 份档案命中第7节或第5节，朝日/露娜无
B1 表格断裂：脚本逐行检测 → 0 处
B3 编号连续：提取 1..12 → 连续无重复
C1 扮演者入口：新表已写入「新会话启动提示词」第三步 + §7 第 11 项
C3 运行中会话：**未自动获得**，已给出可转发说明
E3 密钥扫描：0 命中
```

**⚠️ 若某条查不了，必须写明"查不了 + 原因"**，不得含糊写成"已检查"。
